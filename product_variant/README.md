# 产品变体（安全加属性 / 变体映射）

Odoo 19 `product` 模块扩展：给产品**追加属性 / 取值**（例如「2 个颜色」再加「2 个尺码」，或单变体产品加一个属性）而**不丢任何既有变体**。

**入口不是一个按钮**：用户照常在产品表单的「属性与变体」页改属性，属性行下方是一张**组合表** —— 这次改动之后会存在的每个**属性组合**各占一行，行里的 **Variant** 下拉指定「由哪条既有变体继续保留它」：留空 = 该组合新建变体，选一条 = 那条变体接着承载（它的库存、单据、价格都跟着走）。没被任何组合认领的既有变体会在表上方**点名**，**保存就不放行**；同一条变体只能占一行，**已经被别的行选走的变体在这一行里是禁用的**（灰显、选不了）：要换位置，先把占着它的那一行改回 `(new variant)` 让出来，再给另一行选。会丢既有变体的改动（删取值 / 删属性）则直接被拒绝，绝不静默归档或删除。

> 模块技术名：`product_variant`（`19.0.7.0.0` 由 `product_variant_conversion` 改名而来；当前 `19.0.13.0.7`：`19.0.7.0.1` 修字段 widget 注册方式、`19.0.7.0.2` 修映射表模板变量名、`19.0.7.0.3` 修面板排版、`19.0.7.0.4` 修「点 Add a line 即报必填缺失」、`19.0.7.0.5` 把映射状态改成前端按需取、`19.0.8.0.0` 映射计算整体搬到前端（编辑期零 RPC）、`19.0.8.0.1` 修「加属性面板无反应」（改读 `getChanges()`）、`19.0.8.0.2` 修虚拟行 id、`19.0.8.0.3` 修「面板不刷新」、`19.0.8.0.4` 修「默认值当成用户选择」、`19.0.9.0.0` 组合唯一约束、`19.0.10.0.0` 映射表反向（组合为行、选变体）、`19.0.11.0.0` 所有属性一律穷举、`19.0.12.0.0` 前端穷举展示 + 后端按需预建、`19.0.12.0.1` 下拉禁用已占变体、`19.0.13.0.0` 面板标题 + 显式保存/丢弃、`19.0.13.0.1` 标题改「变体映射」、`19.0.13.0.2` 修「Save manually 点了没反应」（保存钩子里不能调 `getChanges()`）+ 改属性不再发多余 onchange + 面板下方不放按钮、`19.0.13.0.3` 删除唯一属性后自动复用既有变体、`19.0.13.0.4` 删唯一属性时守卫放行（映射已认领那条变体）、`19.0.13.0.5` 面板说明 / 警告自动换行、`19.0.13.0.6` 核查修订（文档同步到当前实现 + 把「原生直写的安全不变量」写成注释与用例）、`19.0.13.0.7` 修「点 New 后映射表还是上一个产品的」（换记录由 `recompute()` 认 + 状态原地作废 + 新建时面板不显示，见模块 `AGENTS.md` → L2 P4 陷阱 24）—— 见 `CHANGELOG.md`，升级后务必强刷）

## 为什么需要这个模块

Odoo 产品表单「属性与变体」页自带一句警告：

> Warning: adding or deleting attributes will delete and recreate existing variants and lead to the loss of their possible customizations.

这不是吓人。`product.product` 记录正是**库存与所有单据的引用目标**，而 Odoo 的 `_create_variant_ids()` 会删除（删不掉就归档）所有不匹配新组合的既有变体：

| 引用方 | 外键策略（已核对 Odoo 19 源码） | 直接增删属性时的后果 |
|--------|--------------------------------|----------------------|
| `stock.move.line.product_id` | `ondelete='cascade'` | 库存移动明细被**连带删除**，出入库历史直接消失 |
| `sale.order.line` / `purchase.order.line` / `account.move.line` / `stock.quant` | `ondelete='restrict'` | 删除失败 → Odoo 退化为**归档**旧变体并**新建**一条同组合的变体，库存与单据仍指向「归档的老变体」，界面与报表逐渐对不上 |
| `stock.move` / `stock.lot` / `product.supplierinfo` / `stock.warehouse.orderpoint` | 默认 `set null`（字段必填 → 报错）或 `cascade` | 报错中断，或补货规则被删 |

本模块把这条危险的写入路接管下来：**先让每条既有变体锚定到用户确认的组合，再让 Odoo 生成缺失的组合**，因此这些记录会被复用它自己，而不是被新建的记录替代。

## 功能概述

- **不加任何按钮**：用户在原生「属性与变体」页照常编辑，点保存即可
- **保存时自动检测**：前端在保存前调一次 `get_variant_conversion_preview()`，服务端用「只写配置、不碰变体」的试写算出这次改动的影响（不改库）
- **会新增变体 → 组合表多出新行，未认领的既有变体拦住保存**：属性行正下方每个**组合**一行，行里指定由哪条既有变体保留它（留空 = 新建变体）；**还有既有变体没被任何组合认领，保存就不放行**（上方点名还差哪几条）。表单内容一直保持未保存状态，不会写半个库
- **会丢既有变体 → 直接拒绝保存**：删属性取值、删属性行导致变体数变少时，保存被拦住并给出明确提示，绝不静默归档 / 删除
- **属性主数据也拦**：在属性主数据里删除被变体使用的取值、直接写属性行删值 / 删行，同样被拒绝（报错给出处置办法）—— 这条绕过产品表单的路也堵上了
- 映射表里每条变体附**在手数量**（装了 `stock` 时），让「谁带哪个组合」的判断有库存依据
- 每条既有 `product.product` 记录都保留（id 不变）：库存、库存移动明细、批次、销售 / 采购 / 发票行、供应商价格、补货规则继续挂在各自那条记录上
- **归属落库可追溯**：转换台账 + 每个变体一条谱系行 + 变体上可搜索的「所属转换 / 来源变体」，产品表单有台账智能按钮与谱系页，变体列表 / 搜索也能按来源追溯
- **价格数据默认按变体分离**：模板级的供应商价格 / 价格表规则拆成每条变体一份（数值不变），新变体从谱系来源继承 —— 每个变体的价格都能各自改，不会牵动别的变体
- 映射表下方有勾选框**把既有变体的供应商价格应用到全部变体**（**默认不勾选**）：勾选后价格统一回模板级一份（所有变体同一批数值）；不勾选就保持上面的「按变体分离」
- 整个转换在**保存点**内执行，并有前置校验与后置断言：任何不符合预期的情况都完全不写库

## 场景覆盖矩阵

「改属性」的所有结局只有下面这几类，本模块逐一处理（✅ = 有自动化测试锁住行为）：

| # | 用户操作 | 变体数 | 模块行为 | 测试 |
|---|----------|--------|----------|------|
| S1 | 单变体产品加一个多取值属性（1 → N） | 变多 | 映射表逐条指定组合，原记录保留在用户指定的组合 | ✅ |
| S2 | **多变体产品加一个新属性（N → N×M）** | 变多 | 同上，每条原记录各自保留一个组合（本模块主场景） | ✅ |
| S3 | 给已有属性追加取值（N → N+M） | 变多 | 同上，同一属性行追加取值 | ✅ |
| S4 | 加一个「只有一个取值」的属性（N → N） | 不变 | 不需要映射（Odoo 自动补取值）：该取值会写到全部变体上 | ✅ |
| S5 | 加「不生成变体」的属性 | 不变 | 不需要映射，原样保存 | ✅ |
| S6 | 重提同一组配置 / 只调属性行顺序 | 不变 | 不需要映射，原样保存 | ✅ |
| S7 | 删属性取值 | 变少 | **拒绝保存**，提示会影响几条变体 | ✅ |
| S8 | 删整个属性行 | 变少 | **拒绝保存**，同上 | ✅ |
| S9 | 改动后被属性配置排除，组合数少于既有变体数 | 变少 | **拒绝保存**，提示先归档或删除不要的变体 | — |
| S10 | 一次改多个产品的属性 | 任意 | 会动到变体 → **拒绝**并提示逐个产品保存；不动到变体 → 放行 | — |
| S11 | 产品带「按需生成变体」的属性（**改属性**） | 变多 | **支持**：映射表穷举列出全部组合（含按需取值）供人分配；**预建**按属性规则 —— 立即轴展开、按需轴只建被既有变体认领的取值，没被认领的按需组合显示成灰色、等 Odoo 在订单里创建 | ✅ |
| S11b | **建产品时**直接带上「按需生成变体」的属性 | 0 | **拒绝**（原生会建出「有属性、没变体」的产品），提示先建产品、保存，再把属性加到产品上 | ✅ |
| S12 | 产品带已归档变体 | 任意 | **拒绝**，提示先恢复或删除（转换不能让老变体悄悄复活；「不新增变体」的改动也不会走原生直写把它激活） | ✅ |

> 「变多才需要映射」的判据是**组合数 > 既有变体数**：组合数不变就没有「新记录由谁承载」这个问题（S4 就是典型）。
> 反过来，组合数变多也不必然每条变体都要重选：已有属性轴上的取值跟着变体走，**只有新轴 / 缺取值的轴**才让该行显示成未映射。

## 数据流：一次转换都发生了什么

```
① 用户在原生「属性与变体」页改属性（不动库）
        ↓
② 点 Save → 前端钩子 FormController.onWillSaveRecord(record, changes)
        ↓  预览 RPC（只读，不改库）
③ product.template.get_variant_conversion_preview([产品], [属性行命令])
   └─ _analyze_variant_conversion_write()：
        快照改动前的属性行与各变体取值 → savepoint →
        带 create_product_product=False 试写属性行（只建 ptav，不碰变体）→
        用 Odoo 自己的组合规则算出「改动后的组合 / 组合数 / 默认归属 / 会丢哪条变体」→
        savepoint.rollback()
        ↓
④ 三种结局（外加两种特例：不新增变体但「原生会丢变体」时走转换、不需要映射；
   产品带「按需生成」属性时所有属性一律穷举，缺失组合由本模块自己补 —— 见「核心设计」）
   ├─ blocked（会丢变体）  → 危险提示，保存中止
   ├─ 有未映射的变体（required 时常见）→ 提示还差几条，保存中止
   │        ↓  用户在映射表里挑好 → 再点 Save：预览算出「每条变体都有组合」
   │        ↓  changes.variant_conversion_mapping = JSON（映射表确认的归属）→ 保存继续
   └─ 其它                → 直接保存
        ↓
⑤ product.template.write()（服务端兜底判定，缺映射一律拒绝）
   ├─ ① create_product_product=False 写属性行（只建 ptav，不删不改任何变体）
   ├─ ② _convert_to_multi_variant()
   │     入口校验 → 配置/归属校验 → SELECT … FOR UPDATE 串行化 → savepoint：
   │       写配置 → 预检（组合数、上限、锚点唯一且未被排除）→
   │       把每条既有变体锚定到它确认后的组合 → _create_variant_ids()（命中即复用，只新建缺失组合）→
   │       后置断言（原变体仍在且带上自己的组合、变体数 == 预期数）→
   │       写转换台账 + 谱系行 + 变体来源字段 →（可选）共享供应商价格
   └─ ③ 本次保存的其余字段（价格等）照常落库 + 清空技术字段
        ↓
⑥ 失败即整单回滚（UserError）；表单保持未保存状态，映射字段仍在，可直接重试
```

## 核心设计

| 设计点 | 说明（为什么这样做） |
|--------|----------------------|
| 拦截点在保存，而不是按钮 | 用户的心智模型就是「改属性 → 保存」；把确认放在保存这一步，既不增加入口，也不会有人绕过它去改属性 |
| 检测用「只写配置、不碰变体」的试写 | 原生写法在「加属性」时本来就会删掉既有变体——那是要防的结果，不是要测量的现象。试写带 `create_product_product=False`（只建 ptav，不触发 `_create_variant_ids`），在保存点里跑一遍再回滚：既有变体毫发无损，也没有「先删再撤」的副作用 |
| 三种结局，各有明确处理 | ① 既有变体一条不少也不新增（只加「不生成变体」的属性、只调顺序、只重提同样的配置）→ 原生保存；② 会新增变体 → 缺取值的变体变**未映射**，映射表里挑好才放行；③ 会丢变体 → 拒绝保存 |
| 「是否需要映射」= 组合数是否变多 | 组合数 > 既有变体数 ⇒ 一定会出现新变体记录 ⇒ 才需要回答「每条既有变体保留哪个组合」；组合数不变（例如只加一个单取值的属性）就没有可映射的东西，直接保存 |
| **前端穷举展示、后端按需预建**（`19.0.12.0.0` 起） | 映射表列出各属性有效取值的笛卡尔积（含「按需生成」属性的全部取值），让人看得全、能提前分配；**预建**则按属性规则：立即轴全部展开，按需轴只建「被既有变体认领的取值」对应的组合（没被认领的行显示灰色 + 提示），缺失组合由本模块调 `_create_product_variant()` 补（`_create_variant_ids()` 对按需属性整段跳过新建）。带按需属性的产品仍然**不做价格分离** —— Odoo 以后还会在订单里为其它取值创建变体，模板级价格要留给它们 |
| 原生会丢变体时自己锚定（映射表不阻断） | 某条既有变体没带上某个**多取值**属性行的取值时，原生 `_create_variant_ids()` 会把它当「组合不完整」删掉 —— 这种情况即便不新增变体也走转换，用默认归属把锚点写下去 |
| 归属是「既有变体 → 组合」的双射 | 映射表按**既有变体**逐行问「它保留哪个组合」；每条既有变体必须恰好指定一个组合，同一组合不能被两条变体占住。服务端把「既有变体 → 它占的取值」写进锚定过程，载荷非法（重复 / 缺一条）一律拒绝 |
| 先锚定、后生成 | 把每条既有变体锚定到它确认后的组合，再调 `_create_variant_ids()`：命中组合的既有变体被复用（既不新建也不删除），只有缺失的组合才新建 |
| 归属与属性变更同一个事务 | 映射表确认的结果通过技术字段 `variant_conversion_mapping` 与用户那组属性命令一起提交，服务端先写配置（不碰变体）、再做安全转换，任何一步失败都整单回滚 |
| 只允许追加 | 删取值会让 Odoo 归档 / 删除对应 ptav 并牵动变体；本模块把它挡在门外，等价于保证「既有变体永不因为改属性而消失」 |
| 后置断言 | 用 Odoo 自己的组合规则算出「应有的组合数」与实际变体数比对，并逐条检查每条既有变体仍存在且带上了自己的组合；不符即整单回滚 |
| 来源判定 | 新变体的来源 = 「改动前就存在的属性轴」上与它一致的那条既有变体（那些属性轴正是改动前各变体相互区分的地方）；判定不唯一时留空，宁可不指也不乱指 |
| 前端只用官方钩子 | 拦截用 `FormController.onWillSaveRecord(record, changes)`（返回 `false` 即阻止保存，`changes` 会原样发给 `web_save`），没有 monkey-patch 保存链路，也不覆写 Odoo 的保存逻辑 |
| 映射表状态存在 model 上 | 面板挂在「属性与变体」页里，切到别的页签会卸载；把「用户选到哪一步」存在 `model.variantMapping` 上，保存钩子与面板共享同一份数据，切页签不丢选择 |
| 服务端才是底线 | 即使前端资源没加载 / 走了命令行或导入路径，服务端的判定与拒绝同样生效——只是没有映射表，用户会收到明确的报错（见「没有映射表时」） |
| 依赖最小化 | 只依赖 `product`：`stock` / `sale` / `purchase` / `account` 未安装或当前用户无权读取时，审计信息自动降级，不影响转换 |

## 怎么用、归属怎么指定

1. 打开产品 → 「属性与变体」页 → 照常加属性、加取值（原生界面）。属性行下方就是**映射表**，改完属性它会自己刷新（防抖 300ms 问一次服务端）。
2. 看映射表：每个**属性组合**一行、每个属性一列（只读），行里的 Variant 下拉指定「由哪条既有变体保留这个组合」：

   | Color | Size | Variant |
   |-------|------|---------|
   | Red   | M    | `(new variant)` ▾ |
   | Red   | L    | `(new variant)` ▾ |
   | Blue  | M    | `(new variant)` ▾ |
   | Blue  | L    | `(new variant)` ▾ |

   （还没分配时每一行的 Variant 都读作 `(new variant)`，表格上方同时有一条警告
   「N existing variants are not assigned to any combination yet」并按名字点名是哪几条。）

   - **行 = 组合**：这次改动之后会存在的组合逐行列出来（所有属性一律按取值穷举，属性列只读）。
   - **未认领 = 这条既有变体没有被任何组合选走**；只要还有未认领的变体，点 Save 就被拦住，表上方点名还差哪几条（表单内容原样保留，接着挑即可）。
   - **Variant 下拉可以留空**（= 该组合新建变体），也可以选任意既有变体；选项标签带在手数量（装了 `stock` 时，形如 `Test App (Red) — 120 on hand`）。同一条变体只能占一行：**已被别的行选走的变体在这一行的下拉里是禁用的**（悬停给出说明），要换位置得先把占着它的行改回 `(new variant)` 让出来。
   - 把 `Red + M` 那行选成 `Test App (Red)`、`Blue + M` 那行选成 `Test App (Blue)`，上方警告消失即可保存；`Red + L` / `Blue + L` 保持 `(new variant)`，保存时由本模块新建。
3. 全部映射好 → 点 **Save**：属性变更与归属映射在同一次写库、同一个事务里落地，转换完成后产品表单自动刷新；点 **Conversions** 在台账详情里核对归属。
4. 映射表下方还列出「本次会新建哪些组合」，以及勾选框「把这些变体的供应商价格应用到全部变体」（**默认不勾选**）：勾上后，仅挂在既有变体上的 `product.supplierinfo` 改为「适用于全部变体」，所有变体取到同一数值；不勾选就保持原样（价格只对原来那条变体生效）。

### 会新增变体时：例子

产品 `Aluminum Bottle` 现有 `Red`、`Blue` 两个变体（各有一批库存与订单行），现在加「Size: M / L」：映射表里两行的 Size 列都变成「Choose a value」、状态 Unmapped —— 这时点保存会被拦住。给 `Red` 选 `M`、给 `Blue` 选 `M`，两行都变 Mapped，保存放行：`Red/M` 与 `Blue/M` 仍是原来那两条记录（库存 120 / 35 与订单行都还在），`Red/L`、`Blue/L` 作为新变体创建。

想交叉指定也行：给 `Blue` 那行选 `L`，则 `Blue/L` 是原记录，新变体变成 `Red/L`、`Blue/M`。

### 会被拒绝的改动

| 改动 | 结果 |
|------|------|
| 删掉某个属性取值（会让带着它的变体失去归属） | 保存被拒绝，报错说明会影响几条变体，并提示「确实要删，先把这些变体归档或删除」 |
| 删掉整个属性行（会让变体数变少） | 同上 |
| 一次改多个产品的属性 | 被拒绝（无法逐条记录归属），提示逐个产品保存 |
| **建产品**时直接带上「按需生成变体」的属性 | 被拒绝（原生会建出没有变体的产品），提示先建产品、保存，再把该属性加到产品上 |
| 产品有已归档变体 | 转换被拒绝（`_create_variant_ids` 可能把老变体重新激活），提示先恢复或删除 |

### 没有映射表时（前端资源未生效）

服务端的判定与拒绝始终生效。若前端资源没加载（例如装完模块没强刷页面），会直接报错：

> Some variants of ... have no combination after this attribute change: pick the combination each of them keeps in the mapping table below the attribute lines, then save again.

按提示强刷一次浏览器（Ctrl+F5），映射表出现后照上面的流程挑完再保存。

## 变体来源与归属怎么追溯

转换会把归属关系**落库**，三层都能查：

| 层次 | 载体 | 能看到什么 |
|------|------|------------|
| 转换台账 | `product.variant.conversion`（产品表单 **Conversions** 智能按钮） | 谁、什么时候、给哪个产品加了哪些属性、变体从几条变几条、新增几条、是否共享了供应商价格 |
| 归属谱系 | `product.variant.lineage`（台账详情页） | 每条变体一行：来源变体 → 结果变体、原记录是否被保留（`is_kept`）、转换前后的组合文本、这次为它新增的取值、结果变体的参考号 / 条码 / 成本 |
| 变体字段 | `product.product.variant_conversion_id` / `variant_origin_id` | 变体表单「Variant Lineage」分组直接显示；变体列表有可选列；变体搜索可按**来源变体 / 所属转换**过滤 |

几个约定：

- `is_kept = True` 的行表示「这个组合就是原来那条记录」——它的库存与单据从来没动过。
- 新变体的 `Derived From` 指向「改动前在**已存在的属性轴**上与它一致」的那条既有变体（例如 `Red/L` 的 `Derived From` 是 `Red/M` 那条记录，也就是原来的 `Red`）。判定不唯一时留空。
- 既有变体的 `Derived From` 为空（它们本身就是来源），但 `Variant Conversion` 会写上，便于按「哪次转换」分组查询。
- 一个产品被转换多次时，`Variant Conversion` 记录最近一次，完整历史在台账与谱系里。

## 已有业务数据怎么处理

转换**不会改动任何历史数据**，处理原则是「谁指向哪条变体，就继续指向哪条变体」：

> **「把原产品资料保留给某个指定变体」为什么不需要转移？**
> 因为映射表里被指定承载某个组合的那条变体，**就是原来那条 `product.product` 记录本身**（id 不变）——
> 内部参考号 `default_code`、条码 `barcode`、按变体的供应商价格（`product.supplierinfo`）、
> 按变体的价格表规则（`product.pricelist.item`，`applied_on = 0_product_variant`）、
> 补货规则（`stock.warehouse.orderpoint`）本来都挂在它身上，转换**一个字段都不搬**。
> 已经指向该变体的记录（`product_id` 就是它）自然不动；模板级的记录（对所有变体生效）也保持模板级。
> 新变体不复制这些资料，只按谱系继承成本 / 体积 / 重量（见「新变体继承策略」）。

| 数据 | 转换后的状态 | 说明 |
|------|--------------|------|
| 在手库存 / 库存量记录（`stock.quant`） | 留在各自那条变体上 | 库存不拆分、不合并；新变体从 0 开始，需要时再自行调拨 / 盘点 |
| 库存移动明细（`stock.move.line`） | 不变 | 历史出入库记录继续指向原变体；这也是最怕被 cascade 删掉的数据 |
| 未完成库存移动（`stock.move`） | 不变 | 在途 / 待处理的拣货、收货继续有效 |
| 批次 / 序列号（`stock.lot`） | 留在各自那条变体上 | 需要按新变体分别管理批次时，由业务上另行处理 |
| 销售订单行（含报价单） | 不变 | 继续指向原来那条变体；如需改到别的变体请手工调整订单行 |
| 采购订单行（含询价单） | 不变 | 同上 |
| 发票 / 日记账分录行（`account.move.line`） | 不变 | 财务数据不受影响 |
| 供应商价格（`product.supplierinfo`） | 默认留在原变体上（**不勾选就是默认**）；映射表里勾选后改为「适用于全部变体」 | 不勾选时新变体没有供应商价格，采购时会找不到价格；勾选会抹平价差，见下文 ⚠ |
| 补货规则（`stock.warehouse.orderpoint`） | 留在各自那条变体上（就是被指定的那条，不动） | 新变体需要各自配置规则 |
| 价格表规则（`product.pricelist.item`） | 按变体的规则（`applied_on = 0_product_variant`）继续指向原来那条变体；按模板的规则（`1_product`）对所有变体生效 | 新变体不会被「按变体」的规则覆盖，需要时另建规则 |

**新变体不会自动获得的东西**（转换后按需补）：内部参考号 `Reference`（`default_code`）与条码、变体图片（`product_image` 模块的变体图集）、供应商价格（除非勾选共享）、补货规则、价格表规则。成本 / 体积 / 重量默认按谱系继承，见下节。

> **原变体的编号会被上移成产品母型号**（`19.0.5.1.0` 起，装了 `product_reference` 时）：单变体产品的编号
> 就是它的产品型号（该模块只在变体上存编号，`G001`），转成多变体后它**上移**到产品的
> `base_reference`（`19.0.5.2.0` 起为覆盖式：以变体编号为准），原变体上的那份被清掉，好让每条变体
> 各填自己的编号（`G001-WT` / `G001-BK`）；值一处不丢。变体本来就没有编号时**什么都不做** ——
> 产品侧若有残留母型号（「多变体退回单变体」的遗留），保留比误删安全。本来就是多变体的产品，
> 转换**不动**任何变体编号。

### 属性归属审计：哪些本来就是变体属性

> **结论：不需要任何数据迁移。**
> ① 条码 / 成本 / 体积 / 重量 / 内部参考号的**真身在变体记录上**，而本模块的铁律是「保留原 `product.product` 记录（id 不变）」——转换后那条默认变体天然带着全部原值，一个字节都不用搬；
> ② 销售价 / 税 / 计量单位**本来就在模板上、全变体共享**，转换根本不碰；产品尺寸（装了 [`product_dimension`](../product_dimension/README.md) 时）是**变体级**的，转换不搬运，由谱系继承带走。
> 唯一会变的是**查看位置**：产品表单上那几个字段在多变体状态下读出来是空 / 0，真值在对应变体上（详见下表与下方说明）。

机制先讲清楚，否则表格看不懂。Odoo 19 里 `product.product` 通过 `_inherits = {'product.template': 'product_tmpl_id'}` **委托**模板字段；
而 `barcode` / `standard_price` / `volume` / `weight` / `default_code` 这几个是 `product.product` **自己声明的存储字段**，在变体上**覆盖**了委托来的模板字段。
于是模板侧那几个变成「单变体桥接」：单变体时读 / 写都落到那条变体（`_compute_template_field_from_variant_field()` / `_set_product_variant_field()`），
一变多之后读出来是默认值（空 / 0）、写进去也不落任何变体 —— **这是 Odoo 原生语义，任何多变体产品都一样，与本模块无关**。

| 字段 | 后端真身（存储在哪） | 普通产品（单变体）时 | 转换后（多变体） | 默认变体上的值 | 需要迁移？ |
|------|----------------------|----------------------|------------------|----------------|------------|
| 内部参考号 `default_code` | **变体**（`product.product` 存储字段） | 产品表单显示那条变体的值 | 产品表单显示空（改显示母型号 `Base Ref.`，即 `product_reference` 的 `base_reference`） | **单变体产品转多变体时**：编号升级为产品母型号、变体上清空；**本来就是多变体**：原值保留 | 不需要 |
| 条码 `barcode` | **变体**（存储字段，唯一性按变体校验） | 同上 | 同上 | **原值保留** | 不需要 |
| 成本 `standard_price` | **变体**（存储字段，按公司隔离） | 同上 | 同上 | **原值保留** | 不需要 |
| 体积 `volume` | **变体**（存储字段） | 同上 | 同上 | **原值保留** | 不需要 |
| 重量 `weight` | **变体**（存储字段） | 同上 | 同上 | **原值保留** | 不需要 |
| 销售价 `list_price` | **模板**（变体侧只是 `related='product_tmpl_id.list_price'` 的委托） | 产品表单显示模板价 | 产品表单不变 | 全变体共享同一价 | 不需要 |
| 属性加价 `price_extra` | 属性取值（`product.template.attribute.value`） | — | — | 随取值自动带上 | 不需要 |
| 产品尺寸（`product_dimension`） | **变体**（`dimension_unit` / `dimension_length` / `dimension_width` / `dimension_height`；模板侧只是单变体桥接） | 产品表单（单变体时） | 产品表单隐藏，到变体表单逐条维护 | **原值保留** | 不需要 |
| 参考号（`product_reference`） | **两层**：产品级共享行（`product_tmpl_id`，产品表单维护）/ 变体级行（`product_id`，变体表单维护）；母型号 `base_reference` 在模板上 | 产品表单（单变体时） | 产品表单隐藏 `Ref.`，改显示母型号 `Base Ref.` | **产品级共享行交接给被保留的变体**；变体级行留在原变体上；母型号留在产品上 | 不需要（行随主人走，不搬值） |
| 税 `taxes_id` / 计量单位 `uom_id` / 产品分类 | **模板** | 产品表单 | 产品表单不变 | 全变体共享 | 不需要 |

**所以「转换后我的条码 / 成本 / 重量去哪了」的标准答案**：没丢，仍在原来那条变体记录上——也就是映射表里被指定承载库存与单据的那条。
去**变体表单或变体列表**看和改（产品表单上的这几个字段在多变体产品上本来就不代表某一条变体）。

> 字段层级由自动化测试 `test_field_storage_layers_match_the_audit()` 钉住：Odoo 升级若改动存储层级，测试会先失败，提醒重新评估是否需要迁移。

### 价格与库存的同步规则

**库存：一个字都不动。** 不拆分、不合并、不迁移，新变体从 0 开始；这就是「保留原 `product.product` 记录」换来的结果。

**转换不会搬运的价格类数据**（上面审计表之外的补充）：

| 数据 | 归属 | 转换后的结果 |
|------|------|--------------|
| 供应商价格 `product.supplierinfo` | 可只挂某条变体，也可挂整个模板 | **默认按变体分离**：模板级的记录拆成每条变体一份（数值不变），新变体再从谱系来源继承一份；勾选「应用到全部变体」才统一为模板级同一批数值（见下方 ⚠） |
| 价格表规则 `product.pricelist.item` | `applied_on = 0_product_variant` 只管一条变体，`1_product` 管整个模板 | **按变体分离**：本产品模板级的规则拆成每条变体一份（数值不变），新变体从谱系来源继承 |
| 成本 `standard_price` | 变体级（见审计表） | 既有变体各自保留；新变体按谱系继承来源（见下节「新变体继承策略」） |

### 新变体继承策略（默认开启，可关）

新变体不是「凭空一条空记录」：默认会从它的**谱系来源**（`Derived From`，即它与之一致的那条既有变体）复制下面这三样变体级数据。

**「来源」怎么认（`19.0.5.0.0` 起）**：只看**转换前就存在的取值** —— 新变体在老属性轴上保留着的那部分取值，与哪条既有变体一致就跟哪条（一致的有多个时取最具体的那个，仍并列就判为不唯一、留空）。所以**给已有属性加取值**时（例如 `Color × Size` 的产品把 `Size` 从 `M` 加到 `M / L`），`Red/L` 也能准确认出它来自 `Red/M`；旧算法只看属性轴、且把**新加的取值**也算进比对，多条原变体时新变体一律「无来源」，尺寸与体积就此丢失。

| 字段 | 是否继承 | 为什么 |
|------|----------|--------|
| 成本 `standard_price` | ✅ 继承来源 | 新规格通常成本相近；不继承就是 0，毛利报表会失真 |
| 体积 `volume` | ✅ 继承来源 | 外贸算运费要用，宁可先给一个可改的值，也别是 0 |
| 重量 `weight` | ✅ 继承来源 | 同上 |
| 产品尺寸（`dimension_unit` / `dimension_length` / `dimension_width` / `dimension_height`，装了 `product_dimension` 时） | ✅ 继承来源（**仅在来源尺寸齐全时**） | 尺寸是体积的来源，只继承体积会让新变体「有体积、没尺寸」；来源尺寸不齐（长宽高有 0）时不复制尺寸，否则会触发该模块「尺寸不齐 → Volume 归 0」把继承来的体积冲掉 |
| 内部参考号 `default_code` | ❌ 不继承 | 本仓库 `product_reference` 的 L1 约束是「**多变体产品不共用参考号**」，复制会与它冲突；新变体应各有可区分的参考号 |
| 条码 `barcode` | ❌ 不继承 | `product.product.barcode` 有**唯一性约束**（`_check_barcode_uniqueness()`），复制必然报错 |
| 价格表规则 `product.pricelist.item` | ✅ 按变体分离后从来源继承 | 本产品模板级规则先拆成每条变体一份，新变体再继承它来源那份 —— 每个变体的售价都能各自改 |
| 补货规则 `stock.warehouse.orderpoint` | ❌ 不继承 | 每个仓库 / 位置一条，复制容易造成重复补货；需要时给新变体单独建 |
| 供应商价格 `product.supplierinfo` | ✅ 默认分离：新变体继承来源一份；勾选「应用到全部变体」时改为所有变体共用同一批 | 见上文「价格数据按变体分离」 |

**关闭方式**：系统参数 `product_variant.inherit_variant_data` 设为 `0`（或 `false` / `no` / `off`）→ 新变体的成本 / 体积 / 重量保持 Odoo 默认的空 / 0，完全由你自己填。

**谱系来源为空时**（判定不唯一）不复制、保持空值——宁可留空让你填，也不乱指一个来源。是否继承了数据会记在转换台账的 **Variant Data Inherited** 列上，可追溯。

> ⚠ **供应商价格共享的代价**（勾选框**默认不勾选**，要主动勾才会发生）：同一供应商若对不同既有变体给了**不同价格**（例如红色 10、蓝色 12），勾选共享后两条都会变成「适用于全部变体」的同级价格记录；采购取价按「折后价 → 序号 → id」排序，只会用上其中一条（通常是便宜的那条）。**要保留变体级价差，就不要勾选共享。**

### 价格数据按变体分离（默认）

**模板级的价格记录 = 一条记录被所有变体共用**：改一次就影响全部变体，这与「变体的价格要各自独立」冲突。所以转换**默认把价格数据按变体分离**：

| 数据 | 转换后 |
|------|--------|
| 本产品**模板级**的供应商价格 / 价格表规则 | 按变体各复制一份（**数值完全不变**）后，**删除原来那条模板级记录** —— 从此每条变体一份，各自可改 |
| 已经**按变体**的记录（`supplierinfo.product_id`、`pricelist.item.applied_on = 0_product_variant`） | 不动（本来就已经分离） |
| **新变体** | 从它的谱系来源（`Derived From`）继承一份，来源没有就留空 |
| `3_global`（所有产品）/ `2_product_category`（按分类）的价格表规则 | **绝不触碰**（它们不属于本产品） |

两条安全线：

1. **绝不静默改价** —— 若变体在同一「价格表 + 数量门槛」上已有自己的规则，模板级规则不再拆过去（否则会凭空多出一条同档规则、把原来生效的那条挤掉）。
2. **后置断言**：分离前后逐条变体校验「供应商价格只多不少」「原有变体的**实际售价**一分未变」「新变体的售价与其来源一致」，不符即整单回滚。

**关闭方式**：系统参数 `product_variant.separate_variant_prices` 设为 `0`（或 `false` / `no` / `off`）→ 模板级记录保持模板级（所有变体共用，改一条影响全部）。是否分离会记在转换台账的 **Variant Prices Separated** 列上。

> 想在转换时反过来把价格**统一**给全部变体？在映射表下方勾选「把这些变体的供应商价格应用到全部变体」即可（供应商价格回到模板级一份；价格表规则仍按变体分离）。

## 模型字段

### `product.template`（扩展）

| 字段 / 方法 | 类型 | 说明 |
|------|------|------|

## 使用前提与限制

- 产品必须有**至少一个变体**，且不是组合产品（`type != 'combo'`）
- 产品**不能有已归档变体**：请先恢复或删除。否则 `_create_variant_ids` 可能把老变体重新激活，归属会变得不可控
- 面板本身有一层「未保存」的保护：映射一改，面板下方（以及表单右上角的状态指示器）出现
  **Save manually** / **Discard all changes**；丢弃会把属性行与映射一起回滚到最后一次保存的状态。
  存在未映射的既有变体时保存被拦住，而且**不会被 Odoo 的自动保存绕过去**（映射不在 record 里，
  自动保存不会带上它）。原生那句「改属性会删掉并重建变体」的警告（`product.product_template_only_form_view`）
  在本模块下已不成立，已随视图继承删除。
- 产品可以带「按需生成」的属性（`attribute.create_variant == 'dynamic'`）：映射表**穷举列出**全部组合（含按需属性的全部取值）供人分配，但**预建**按属性规则 —— 按需轴只建被既有变体认领的取值，其余等 Odoo 在订单里创建。带按需属性的产品**不做价格分离**（价格记录保持模板级共享，否则以后订单期新建的变体会取不到价格）
- **建产品时**不要直接带「按需生成」的属性：原生 `create()` 遇到它会一条变体都不建（变体等到下单才创建），会留下「有属性、没变体」的产品 → 本模块会拦住并提示「先不带该属性建产品、保存，再把属性加到产品上」
- **不能通过本流程删取值 / 删属性**：这类改动会让既有变体失去归属，一律拒绝。确实要删，请先归档或删除不想要的变体，再改属性配置
- **一次只能保存一个产品**：多记录写入无法逐条记录归属，会被拒绝
- 变体数受系统参数 `product.dynamic_variant_limit`（默认 1000）限制，超限会直接拒绝并说明数量

## 已知边界与后续迭代

### 已知边界（当前实现如此，不是 bug）

| 边界 | 说明 |
|------|------|
| 直接写路径只覆盖「删除类」改动 | 归属确认挂在 `product.template.write()` 上；绕过它的**删除类**路径已由 `models/product_attribute_guards.py`（`T-017`）一并拦住：属性主数据里删取值（`product.attribute.value.unlink()`，取值已被产品使用时拒绝）、删取值记录（`product.template.attribute.value.unlink()`，还有在用变体带着它时拒绝）、直接写属性行移走取值 / 删行（`product.template.attribute.line.write()/.unlink()`）都有守卫，且都有自动化测试。**未覆盖的是「新增行」**（`product.template.attribute.line.create()`，见下表最后一行）。 |
| 映射表挂在「属性与变体」页里 | 面板只在属性行下方渲染，切到别的页签它就卸载；「用户选到哪一步」存在 `model.variantMapping` 上，切回来原样恢复。保存钩子不依赖面板是否挂载 —— 从别的页签点保存，判定与拦截同样生效。 |
| 面板只在**已保存的产品**上显示（`19.0.13.0.7` 起） | 新建（还没保存、没有 id）时没有既有变体可映射，面板整块不显示；点 **New** / 用分页翻到别的产品时，上一份映射（行 / 分配 / 基线 / 未保存标记）整个作废并重取快照，快照取回来之前面板先隐藏 —— 不会把上一条产品的映射当成这一条的（见模块 `AGENTS.md` → L2 P4 陷阱 24）。产品保存后拿到 id，面板自动出现。 |
| 继承范围有限 | 新变体按谱系继承**成本 / 体积 / 重量**与**价格数据**（价格表规则、供应商价格）；参考号、条码、补货规则刻意不继承（各有硬约束，见「新变体继承策略」）。来源为空时也留空，不猜测。 |
| 分离会拆掉模板级价格记录 | 默认分离时，本产品模板级的供应商价格 / 价格表规则被**拆分后删除**（值完整保留在各变体上，后置断言保证售价一分未变）。不想拆就关掉系统参数 `product_variant.separate_variant_prices`。**带「按需生成」属性的产品一律不做分离**（以后订单期新建的变体还要靠模板级价格）。 |
| 供应商价格共享会抹平变体级价差 | 见上文 ⚠（勾选框默认不勾选，不会自动发生）。 |
| 谱系行随变体级联删除 | `product.variant.lineage` 的两个变体字段是 `ondelete='cascade'`：删掉一条变体，它在谱系里的行会一起消失（转换台账本身不受影响）。 |
| 组合数特别大的产品 | 组合枚举没有前置上限保护，会先枚举出全部组合、再撞 `product.dynamic_variant_limit`；超大产品请先精简属性取值。 |
| 无法撤销一次转换 | Odoo 没有内置回滚，转换前请备份。 |
| 映射表没有浏览器级自动化测试 | 服务端测试（`19.0.13.0.6` 时 **66 项**）覆盖主流程、关键拒绝路径、属性主数据拦截、字段归属、继承策略、价格分离与原产品资料保留（尚未覆盖的分支见模块 `AGENTS.md` → L2 P5 缺口 9）；面板的纯函数（组合行 / 默认分配 / 未分配清单 / 载荷）另有 `tests/js/variant_mapping_pure.mjs` 覆盖，但**要手工跑** `node product_variant/tests/js/variant_mapping_pure.mjs`（`task check` 只做 JS 语法检查，不执行它）；真正的 DOM 交互（下拉禁用、切页签、保存钩子）仍靠手工验证（见「验证清单」）。 |
| 归档属性取值不拦截 | 删除被变体使用的取值会被拒绝；但**归档**它不拦（Odoo 原生也不拦）——归档后变体仍带着该取值，界面与后续写入会不一致。处置办法与删取值相同：先处理变体。 |
| combo 分支未自动化测试 | 组合产品（`type = combo`）的拒绝守卫存在，但构造合法组合产品需要先配 combo choice，未写自动化测试（手工验证见「验证清单」）。 |
| 「按需生成」属性是**支持的**，所有属性一律穷举（`19.0.11.0.0` 起） | Odoo 的产品导入（`product.product._load_records_create()`）会把新建属性自动设成「按需生成」、并自己逐行建变体 —— 导入来的产品现在可以正常改属性：转换所有属性一律穷举，按需轴按每条既有变体现带的取值钉住，**它的其它取值不预建变体**（等订单创建）；带按需属性的产品不做价格分离。两个残留边界：① **建产品时**不能直接带这种属性（原生会建出 0 变体的产品，本模块拦住并给出出路）；② 纯按需且 0 变体的产品本模块不介入（没有既有变体可保，属性改动原样交给原生）。 |
| 按需生成产品的变体由 Odoo 在**订单期**创建，本模块当时不接管 | 订单期的入口是配置器 → `sale.order.line` → `product.template._create_product_variant()` → `product.product.create()`，全程不经过 `product.template.write()`：本模块**不拦、也不给它补数据** —— 没有 `Variant Conversion` / `Derived From`、没有谱系行、不写台账、不做按谱系继承（继承只发生在本模块自己的转换里）。这些变体是「Odoo 的」；**之后**的属性改动会走本模块的转换，那时新增的变体才有来源与继承。 |
| `attribute.line.create()` **新增行**会绕过本模块 | 属性行守卫只覆盖「移走取值 / 删行」；`product.template.attribute.line.create()`（非沙盒上下文）自己会调 `_create_variant_ids()`：对按需生成的产品，新加一行会让既有变体的组合变得「不完整」，原生会把它们**删除**（实测：2 条在用变体直接消失）。这是 `T-017` 的剩余缺口，见 `AGENTS.md` → L2 P5 缺口 1。 |

- **应用列表（Apps）元数据**：模块名 / 摘要 / 描述的中文由 `i18n/zh_CN.po` 的 `model:ir.module.module,shortdesc|summary|description:base.module_product_variant` 三条提供，分类沿用官方的 `Inventory/Product`（自定义段 `base.module_category_inventory_product` → 「产品」，与其它产品类模块合并同一条 `msgid`）。改 `__manifest__.py` 的 `name` / `summary` / `description` 时必须同步这三条，规范见根 [`AGENTS.md`](../AGENTS.md) 4.8。
- 占位符统一 `%(name)s` 命名形式，禁止按位置拼接；映射表里夹在元素中的句子（如「还差 N 条」）一律在 JS 侧用 `_t()` 拼好再 `t-esc`，避免被模板切成碎片。
- 改动流程：改英文源文本 → 用官方 `odoo i18n export` 重导出术语骨架 → 按 `msgid` 合并回 `i18n/zh_CN.po` → `task check` → `-u` 升级 + 强刷浏览器，英文与中文各验一遍（做法见模块 `AGENTS.md` → L2 P3）。
- 本模块 `i18n/zh_CN.po` 现有 132 条条目（128 条来自官方导出骨架 + 4 条应用列表元数据：`shortdesc` / `summary` / `description` / 分类），`msgid` 与源码逐字符一致；只有 6 条标准审计字段标签（`Created by` 等，界面上不显示）没有译文。

## 依赖

- `product`（必需）：属性、属性取值、产品变体都来自它。
- **不依赖** `stock` / `sale` / `purchase` / `account`：预览里的在手数量、台账展示在运行时会判断这些模型是否存在（`model_name in self.env`）以及当前用户是否有读权限，缺哪个就降级显示，不影响转换。测试里也先判断 `is_storable`（由 `stock` 提供）是否存在。

### 可选集成与解耦边界

对可选模块的**全部了解都收在适配层**（`models/product_template.py` →「可选集成适配层」注释：
`_has_base_reference_field()` / `_has_shared_reference_lines()` / `_get_reference_code_model()`），
对方缺失时一律**空转降级**，绝不中断转换、也绝不直接 `env[对方模型名]`（那会是 `KeyError`）。
对方改名 / 改字段只需改适配层那一处。

| 可选模块 | 接入点 | 装了时的行为 | 缺席时的降级行为（主流程照常走完） |
|----------|--------|--------------|------------------------------------|
| [`product_reference`](../product_reference/README.md) | 适配层三个方法（`base_reference` 字段 / `reference_code_line_ids` 字段 / `product.reference.code` 模型） | ① 单变体编号**上移**成产品母型号；② 产品级共享参考号**交接**给被保留的变体 | ① 编号留在原变体上（没有任何地方可上移）；② 参考号行留在产品级（数据不丢，只是多变体产品的产品表单不显示它们）。两条都由 `test_reference_handling_degrades_gracefully_without_product_reference()` 在两种配置下分别断言 |
| [`product_dimension`](../product_dimension/README.md) | `_get_variant_conversion_inherited_fields()` 按字段存在性 | 新变体按谱系继承尺寸四件套（仅来源尺寸齐全时） | 只继承成本 / 体积 / 重量 |
| `stock` / `sale` / `purchase` / `account` / `mail` | `"模型" in env` / `hasattr` | 映射表显示在手数量、chatter 留痕 | 对应信息省略 |

> ⚠ **本模块是三者中唯一改动核心写行为的**：装了它之后，`write({'attribute_line_ids': ...})`
> （改属性的保存）会被拦截并要求确认变体归属 —— 这是功能本身，不是副作用。
> **其它模块的代码 / 测试若需要程序化产生多变体产品，请把属性行放进 `create()`**
> （`create` 不拦截），不要用「先建单变体、再 `write` 属性行」的写法。
> 反向：本模块**不向任何模块提供接口**，卸载它不影响 `product_reference` / `product_card_view`。

## 安装与使用

### 全新安装

1. 将 `product_variant` 目录放入 Odoo 19 的 `addons_path`
2. 更新应用列表后安装模块：**产品变体**
3. **强刷一次浏览器**（Ctrl+F5）：本模块的保存拦截与映射表是前端资源，必须让页面加载到最新资产

### 从旧版本升级

`19.0.2.0.0` 及更早的版本用的是「产品表单按钮 + 向导」。`19.0.3.0.0` 起改为「保存时拦截 + 弹窗」，向导模型（`product.variant.conversion.wizard` 等）已删除：瞬态模型，无数据迁移，**不需要迁移脚本**。`19.0.7.0.0` 起弹窗换成「属性与变体」页下方的映射表，升级后请强刷浏览器。

### 从 `product_variant_conversion` 改名升级（**已经在用的库必读**）

Odoo 把模块目录名当作模块身份：只改目录而不动库，等于「旧模块凭空消失 + 新模块没装」，
Odoo 启动时会因为找不到已装的 `product_variant_conversion` 而报错。

`19.0.7.0.0` 换的**只有技术名**：模型名 `product.variant.conversion` / `product.variant.lineage`、
所有字段（含列）、视图 / 动作 / 权限的 xmlid 一律未动，所以**原地改名即可，不需要卸载重装**：

```bash
# 0. 备份数据库（要 UPDATE，先备份）
# 1. 停 Odoo；把 product_variant 放进 addons_path，旧目录 product_variant_conversion 移走
# 2. 原地改名：把「模块身份」从旧名迁到新名（三条 SQL）
psql -d <db> <<'SQL'
UPDATE ir_module_module SET name = 'product_variant' WHERE name = 'product_variant_conversion';
UPDATE ir_model_data SET module = 'product_variant' WHERE module = 'product_variant_conversion';
UPDATE ir_model_data SET name = 'module_product_variant'
 WHERE module = 'base' AND name = 'module_product_variant_conversion';
SQL
# 3. 升级（版本号要比库里的 latest_version 大；19.0.7.0.0 满足）
odoo -d <db> -u product_variant --stop-after-init
# 4. 强刷浏览器（Ctrl+F5）：映射表与保存拦截都是前端资源
```

- 第 1 条改的是模块记录本身；
- 第 2 条把本模块所有 XML ID（视图 / 动作 / 权限）迁到新名下 —— **不改**的话升级时
  `_process_end()` 会因为「这些 xmlid 不在本次加载的模块里」而把对应记录删掉；
- 第 3 条是「应用」列表那条元数据：模块名 / 摘要 / 描述的译文挂靠在 `base.module_<技术名>`
  这个 xmlid 上，它的归属是 `base`，不会被第 2 条带到。

**走这条路，台账 / 谱系 / 变体上的来源字段一条都不丢**（表名与列名都没变）。
反过来，**卸载旧模块再装新模块会清空台账、谱系与变体来源字段**（`unlink` 删表删列），
只有在确认这些历史不要了的时候才这么做。

改名后系统参数前缀从 `product_variant_conversion.` 变成 `product_variant.`：新参数没设过时
**仍会回退读旧名**，之前改过的开关不会静默失效。

### 操作

- 改属性 → 看映射表里有没有「未映射」的变体 → 逐条挑好 → 保存
- 转换完成后点 **Conversions** 看台账（详情页里有完整归属谱系）

```bash
# 连库存 / 销售一起验证（推荐，会额外装上 stock 与 sale_management）

```

### 异常情况与处理

- **点保存弹出危险提示「会归档或删除 N 条既有变体」**：说明这次属性改动是删减类的。先归档或删除不想要的变体，再改属性配置。
- **点保存报错说「有变体没有组合」，但没看到映射表**：前端资源没生效，强刷页面（Ctrl+F5）后再保存一次。
- **保存总是被拦住，提示还有变体没有组合**：映射表里还有 Unmapped 的行，表底部会提示还差几条；每条变体都挑完取值（状态列全变 Mapped）才能保存。
- **报「有归档变体」**：先在产品变体列表里恢复或删除它们，再改属性。
- **报「按需生成变体」（`creates its variants on demand`）**：报错里已点名是哪个属性。处置顺序不能颠倒 —— Odoo **不允许**修改「已被产品使用」的属性的变体生成方式（会报 `You cannot change the Variants Creation Mode of the attribute ...`）：先把该属性从产品上移除（属性行里带着它取值的**在用变体**要先归档或删除，否则属性行的删除守卫会拦住），再去属性设置里把「变体生成方式」改成「立即」，最后把它加回产品。**建产品时**就带按需生成属性的话，第一次保存就会被拦（原生 `create()` 会建出一个没有变体的产品），此时属性还没被任何产品使用，直接去改属性设置再重存即可。
- **想撤销一次转换**：Odoo 没有内置回滚。可在转换后立刻把新变体归档并删掉多余属性取值（原生界面会给出警告），或从备份恢复；**转换前请先备份**。
