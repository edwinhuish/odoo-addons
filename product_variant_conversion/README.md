# 产品变体转换

Odoo 19 `product` 模块扩展：给产品**追加属性 / 取值**（例如「2 个颜色」再加「2 个尺码」，或单变体产品加一个属性）而**不丢任何既有变体**。

**入口不是一个按钮**：用户照常在产品表单的「属性与变体」页改属性、点保存，**保存这一步自己检测**这次变更有没有动到既有变体——会新增变体就弹出模态框，让用户逐个组合地指定「由哪条既有变体继续承载」；用户确认归属之前，保存不会继续。会丢既有变体的改动（删取值 / 删属性）则直接被拒绝，绝不静默归档或删除。

> 模块技术名：`product_variant_conversion`  
> 无前身模块，首次安装即可使用。

---

## 为什么需要这个模块

Odoo 产品表单「属性与变体」页自带一句警告：

> Warning: adding or deleting attributes will delete and recreate existing variants and lead to the loss of their possible customizations.

这不是吓人。`product.product` 记录正是**库存与所有单据的引用目标**，而 Odoo 的 `_create_variant_ids()` 会删除（删不掉就归档）所有不匹配新组合的既有变体：

| 引用方 | 外键策略（已核对 Odoo 19 源码） | 直接增删属性时的后果 |
|--------|--------------------------------|----------------------|
| `stock.move.line.product_id` | `ondelete='cascade'` | 库存移动明细被**连带删除**，出入库历史直接消失 |
| `sale.order.line` / `purchase.order.line` / `account.move.line` / `stock.quant` | `ondelete='restrict'` | 删除失败 → Odoo 退化为**归档**旧变体并**新建**一条同组合的变体，库存与单据仍指向「归档的老变体」，界面与报表逐渐对不上 |
| `stock.move` / `stock.lot` / `product.supplierinfo` / `stock.warehouse.orderpoint` | 默认 `set null`（字段必填 → 报错）或 `cascade` | 报错中断，或补货规则被删 |

本模块把这条危险的写入路接管下来：**先让每条既有变体锚定到用户确认的组合，再让 Odoo 生成缺失的组合**，因此这些记录会被复用它自己，而不是被新建的记录替代。

---

## 功能概述

- **不加任何按钮**：用户在原生「属性与变体」页照常编辑，点保存即可
- **保存时自动检测**：前端在保存前调一次 `get_variant_conversion_preview()`，服务端用「只写配置、不碰变体」的试写算出这次改动的影响（不改库）
- **会新增变体 → 弹出归属确认框**：弹窗逐个组合地列出「改动后的组合」，每个组合可选一条既有变体作为「由谁继续承载」（默认值已按「什么都不指定时的结果」填好，可逐行改）；**用户确认之前保存不继续**，取消 / 关掉弹窗就等于本次不保存（表单内容保持未保存状态，可直接再点保存重新确认）
- **会丢既有变体 → 直接拒绝保存**：删属性取值、删属性行导致变体数变少时，保存被拦住并给出明确提示，绝不静默归档 / 删除
- 每条既有 `product.product` 记录都保留（id 不变）：库存、库存移动明细、批次、销售 / 采购 / 发票行、供应商价格、补货规则继续挂在各自那条记录上
- **归属落库可追溯**：转换台账 + 每个变体一条谱系行 + 变体上可搜索的「所属转换 / 来源变体」，产品表单有台账智能按钮与谱系页，变体列表 / 搜索也能按来源追溯
- **价格数据默认按变体分离**：模板级的供应商价格 / 价格表规则拆成每条变体一份（数值不变），新变体从谱系来源继承 —— 每个变体的价格都能各自改，不会牵动别的变体
- 弹窗里可勾选**把既有变体的供应商价格应用到全部变体**（**默认不勾选**）：勾选后价格统一回模板级一份（所有变体同一批数值）；不勾选就保持上面的「按变体分离」
- 整个转换在**保存点**内执行，并有前置校验与后置断言：任何不符合预期的情况都完全不写库

## 场景覆盖矩阵

「改属性」的所有结局只有下面这几类，本模块逐一处理（✅ = 有自动化测试锁住行为）：

| # | 用户操作 | 变体数 | 模块行为 | 测试 |
|---|----------|--------|----------|------|
| S1 | 单变体产品加一个多取值属性（1 → N） | 变多 | 弹窗确认归属，原记录保留在用户指定的组合 | ✅ |
| S2 | **多变体产品加一个新属性（N → N×M）** | 变多 | 同上，每条原记录各自保留一个组合（本模块主场景） | ✅ |
| S3 | 给已有属性追加取值（N → N+M） | 变多 | 同上，同一属性行追加取值 | ✅ |
| S4 | 加一个「只有一个取值」的属性（N → N） | 不变 | 不弹窗：Odoo 会把该取值自动写到全部变体上 | ✅ |
| S5 | 加「不生成变体」的属性 | 不变 | 不弹窗，原样保存 | ✅ |
| S6 | 重提同一组配置 / 只调属性行顺序 | 不变 | 不弹窗，原样保存 | ✅ |
| S7 | 删属性取值 | 变少 | **拒绝保存**，提示会影响几条变体 | ✅ |
| S8 | 删整个属性行 | 变少 | **拒绝保存**，同上 | ✅ |
| S9 | 改动后被属性配置排除，组合数少于既有变体数 | 变少 | **拒绝保存**，提示先归档或删除不要的变体 | — |
| S10 | 一次改多个产品的属性 | 任意 | 会动到变体 → **拒绝**并提示逐个产品保存；不动到变体 → 放行 | — |
| S11 | 产品带「按需生成变体」的属性 | 任意 | **拒绝**，提示先把该属性的变体生成方式改为「立即」 | — |
| S12 | 产品带已归档变体 | 任意 | **拒绝**，提示先恢复或删除（转换不能让老变体悄悄复活） | — |

> 「变多才需要确认」的判据是**组合数 > 既有变体数**：组合数不变就没有「新记录由谁承载」这个问题（S4 就是典型）。

## 数据流：一次转换都发生了什么

```
① 用户在原生「属性与变体」页改属性（不动库）
        ↓
② 点 Save → 前端钩子 FormController.onWillSaveRecord(record, changes)
        ↓  预览 RPC（只读，不改库）
③ product.template.get_variant_conversion_preview([产品], [属性行命令])
   └─ _analyze_variant_conversion_write()：
        快照改动前的属性行与各变体取值 → savepoint →
        带 create_product_product=False 试写属性行（只建 ptav，不碰变体）→
        用 Odoo 自己的组合规则算出「改动后的组合 / 组合数 / 默认归属 / 会丢哪条变体」→
        savepoint.rollback()
        ↓
④ 三种结局
   ├─ blocked（会丢变体）  → 危险提示，保存中止
   ├─ required（会新增变体）→ 弹出归属确认框（默认归属已填好）→ 用户确认
   │        ↓  record.update({variant_conversion_mapping: JSON}) + 重新保存
   └─ 其它                → 直接保存
        ↓
⑤ product.template.write()（服务端兜底判定，缺映射一律拒绝）
   ├─ ① create_product_product=False 写属性行（只建 ptav，不删不改任何变体）
   ├─ ② _convert_to_multi_variant()
   │     入口校验 → 配置/归属校验 → SELECT … FOR UPDATE 串行化 → savepoint：
   │       写配置 → 预检（组合数、上限、锚点唯一且未被排除）→
   │       把每条既有变体锚定到它确认后的组合 → _create_variant_ids()（命中即复用，只新建缺失组合）→
   │       后置断言（原变体仍在且带上自己的组合、变体数 == 预期数）→
   │       写转换台账 + 谱系行 + 变体来源字段 →（可选）共享供应商价格
   └─ ③ 本次保存的其余字段（价格等）照常落库 + 清空技术字段
        ↓
⑥ 失败即整单回滚（UserError）；表单保持未保存状态，映射字段仍在，可直接重试
```

## 核心设计

| 设计点 | 说明（为什么这样做） |
|--------|----------------------|
| 拦截点在保存，而不是按钮 | 用户的心智模型就是「改属性 → 保存」；把确认放在保存这一步，既不增加入口，也不会有人绕过它去改属性 |
| 检测用「只写配置、不碰变体」的试写 | 原生写法在「加属性」时本来就会删掉既有变体——那是要防的结果，不是要测量的现象。试写带 `create_product_product=False`（只建 ptav，不触发 `_create_variant_ids`），在保存点里跑一遍再回滚：既有变体毫发无损，也没有「先删再撤」的副作用 |
| 三种结局，各有明确处理 | ① 既有变体一条不少也不新增（只加「不生成变体」的属性、只调顺序、只重提同样的配置）→ 原生保存；② 会新增变体 → 弹窗确认归属；③ 会丢变体 → 拒绝保存 |
| 「是否需要确认」= 组合数是否变多 | 组合数 > 既有变体数 ⇒ 一定会出现新变体记录 ⇒ 才需要回答「新组合由谁承载」；组合数不变（例如只加一个单取值的属性）就没有可确认的东西，直接保存 |
| 归属是「组合 ← 既有变体」的双射 | 弹窗按「改动后的组合」逐行问「由哪条既有变体继续承载」；每条既有变体必须恰好被指定一次，同一组合不能有两条来源。用户确认后，服务端把「既有变体 → 它占的取值」写进锚定过程 |
| 先锚定、后生成 | 把每条既有变体锚定到它确认后的组合，再调 `_create_variant_ids()`：命中组合的既有变体被复用（既不新建也不删除），只有缺失的组合才新建 |
| 归属与属性变更同一个事务 | 弹窗确认的结果通过技术字段 `variant_conversion_mapping` 与用户那组属性命令一起提交，服务端先写配置（不碰变体）、再做安全转换，任何一步失败都整单回滚 |
| 只允许追加 | 删取值会让 Odoo 归档 / 删除对应 ptav 并牵动变体；本模块把它挡在门外，等价于保证「既有变体永不因为改属性而消失」 |
| 后置断言 | 用 Odoo 自己的组合规则算出「应有的组合数」与实际变体数比对，并逐条检查每条既有变体仍存在且带上了自己的组合；不符即整单回滚 |
| 来源判定 | 新变体的来源 = 「改动前就存在的属性轴」上与它一致的那条既有变体（那些属性轴正是改动前各变体相互区分的地方）；判定不唯一时留空，宁可不指也不乱指 |
| 前端只用官方钩子 | 拦截用 `FormController.onWillSaveRecord(record, changes)`（返回 `false` 即阻止保存，`changes` 会原样发给 `web_save`），没有 monkey-patch 保存链路，也不覆写 Odoo 的保存逻辑 |
| 服务端才是底线 | 即使前端资源没加载 / 走了命令行或导入路径，服务端的判定与拒绝同样生效——只是没有弹窗，用户会收到明确的报错（见「没有弹窗时」） |
| 依赖最小化 | 只依赖 `product`：`stock` / `sale` / `purchase` / `account` 未安装或当前用户无权读取时，审计信息自动降级，不影响转换 |

## 怎么用、归属怎么指定

1. 打开产品 → 「属性与变体」页 → 照常加属性、加取值（原生界面）。
2. 点 **Save**。若这次改动会新增变体，弹出 **Variant Ownership**：

   | Combination After | Kept By |
   |-------------------|---------|
   | Color: Red, Size: M | Test App (Red) ◂ 下拉可选 |
   | Color: Red, Size: L | New variant（由本次转换创建） |
   | Color: Blue, Size: M | Test App (Blue) |
   | Color: Blue, Size: L | New variant（由本次转换创建） |

   - 左边是改动后会出现哪些组合；右边选**哪条既有变体继续承载这个组合**（它保留库存、订单与发票），其余组合作为新变体创建。
   - 默认值已经按「什么都不指定时的结果」填好（已有属性保持原取值、新加属性取本次第一个取值），大多数情况直接点 **Confirm** 即可。
   - 一条既有变体只能承载一个组合；还有既有变体没被分配时，`Confirm` 不可点，弹窗会提示还差几条。
   - 取消 / 直接关掉弹窗 = 本次不保存，表单保持未保存状态；再点一次保存会重新弹窗。
   - 下面的勾选框「把这些变体的供应商价格应用到全部变体」（**默认不勾选**）：勾上后，仅挂在既有变体上的 `product.supplierinfo` 改为「适用于全部变体」，所有变体取到同一数值；不勾选就保持原样（价格只对原来那条变体生效）。
3. 确认后保存继续：属性变更与归属映射在同一次写库、同一个事务里落地，转换完成后产品表单自动刷新，可到 **Variant Lineage** 页核对。

### 会新增变体时：例子

产品 `Aluminum Bottle` 现有 `Red`、`Blue` 两个变体（各有一批库存与订单行），现在加「Size: M / L」：默认归属是 `Red/M ← Red（原记录）`、`Blue/M ← Blue（原记录）`，`Red/L` 与 `Blue/L` 是新记录——两条原记录的库存（120 / 35）与订单行都还在它们身上。

想交叉指定也行：把 `Blue` 那行改成 `Color: Blue, Size: L`，则 `Blue/L` 是原记录，新变体变成 `Red/L`、`Blue/M`。

### 会被拒绝的改动

| 改动 | 结果 |
|------|------|
| 删掉某个属性取值（会让带着它的变体失去归属） | 保存被拒绝，报错说明会影响几条变体，并提示「确实要删，先把这些变体归档或删除」 |
| 删掉整个属性行（会让变体数变少） | 同上 |
| 一次改多个产品的属性 | 被拒绝（无法逐条记录归属），提示逐个产品保存 |
| 产品有「按需生成变体」的属性 | 被拒绝并提示先把该属性的变体生成方式改为「立即」 |
| 产品有已归档变体 | 转换被拒绝（`_create_variant_ids` 可能把老变体重新激活），提示先恢复或删除 |

### 没有弹窗时（前端资源未生效）

服务端的判定与拒绝始终生效。若前端资源没加载（例如装完模块没强刷页面），会直接报错：

> This attribute change creates new variants of ...: every existing variant has to be told which combination it keeps, so the save is held back until the ownership is confirmed from the product form. Save again from the form to get the dialog; if it does not show up, reload the page (Ctrl+F5) ...

按提示强刷一次浏览器（Ctrl+F5）即可。

## 变体来源与归属怎么追溯

转换会把归属关系**落库**，三层都能查：

| 层次 | 载体 | 能看到什么 |
|------|------|------------|
| 转换台账 | `product.variant.conversion`（产品表单 **Conversions** 智能按钮） | 谁、什么时候、给哪个产品加了哪些属性、变体从几条变几条、新增几条、是否共享了供应商价格 |
| 归属谱系 | `product.variant.lineage`（台账详情页 / 产品表单 **Variant Lineage** 页） | 每条变体一行：来源变体 → 结果变体、原记录是否被保留（`is_kept`）、转换前后的组合文本、这次为它新增了哪些取值 |
| 变体字段 | `product.product.variant_conversion_id` / `variant_origin_id` | 变体表单「Variant Lineage」分组直接显示；变体列表有可选列；变体搜索可按**来源变体 / 所属转换**过滤 |

几个约定：

- `is_kept = True` 的行表示「这个组合就是原来那条记录」——它的库存与单据从来没动过。
- 新变体的 `Derived From` 指向「改动前在**已存在的属性轴**上与它一致」的那条既有变体（例如 `Red/L` 的 `Derived From` 是 `Red/M` 那条记录，也就是原来的 `Red`）。判定不唯一时留空。
- 既有变体的 `Derived From` 为空（它们本身就是来源），但 `Variant Conversion` 会写上，便于按「哪次转换」分组查询。
- 一个产品被转换多次时，`Variant Conversion` 记录最近一次，完整历史在台账与谱系里。

## 已有业务数据怎么处理

转换**不会改动任何历史数据**，处理原则是「谁指向哪条变体，就继续指向哪条变体」：

> **「把原产品资料保留给某个指定变体」为什么不需要转移？**
> 因为弹窗里被指定承载某个组合的那条变体，**就是原来那条 `product.product` 记录本身**（id 不变）——
> 内部参考号 `default_code`、条码 `barcode`、按变体的供应商价格（`product.supplierinfo`）、
> 按变体的价格表规则（`product.pricelist.item`，`applied_on = 0_product_variant`）、
> 补货规则（`stock.warehouse.orderpoint`）本来都挂在它身上，转换**一个字段都不搬**。
> 已经指向该变体的记录（`product_id` 就是它）自然不动；模板级的记录（对所有变体生效）也保持模板级。
> 新变体不复制这些资料，只按谱系继承成本 / 体积 / 重量（见「新变体继承策略」）。

| 数据 | 转换后的状态 | 说明 |
|------|--------------|------|
| 在手库存 / 库存量记录（`stock.quant`） | 留在各自那条变体上 | 库存不拆分、不合并；新变体从 0 开始，需要时再自行调拨 / 盘点 |
| 库存移动明细（`stock.move.line`） | 不变 | 历史出入库记录继续指向原变体；这也是最怕被 cascade 删掉的数据 |
| 未完成库存移动（`stock.move`） | 不变 | 在途 / 待处理的拣货、收货继续有效 |
| 批次 / 序列号（`stock.lot`） | 留在各自那条变体上 | 需要按新变体分别管理批次时，由业务上另行处理 |
| 销售订单行（含报价单） | 不变 | 继续指向原来那条变体；如需改到别的变体请手工调整订单行 |
| 采购订单行（含询价单） | 不变 | 同上 |
| 发票 / 日记账分录行（`account.move.line`） | 不变 | 财务数据不受影响 |
| 供应商价格（`product.supplierinfo`） | 默认留在原变体上（**不勾选就是默认**）；弹窗里勾选后改为「适用于全部变体」 | 不勾选时新变体没有供应商价格，采购时会找不到价格；勾选会抹平价差，见下文 ⚠ |
| 补货规则（`stock.warehouse.orderpoint`） | 留在各自那条变体上（就是被指定的那条，不动） | 新变体需要各自配置规则 |
| 价格表规则（`product.pricelist.item`） | 按变体的规则（`applied_on = 0_product_variant`）继续指向原来那条变体；按模板的规则（`1_product`）对所有变体生效 | 新变体不会被「按变体」的规则覆盖，需要时另建规则 |

**新变体不会自动获得的东西**（转换后按需补）：内部参考号 `Reference`（`default_code`）与条码、变体图片（`product_image` 模块的变体图集）、供应商价格（除非勾选共享）、补货规则、价格表规则。成本 / 体积 / 重量默认按谱系继承，见下节。

### 属性归属审计：哪些本来就是变体属性

> **结论：不需要任何数据迁移。**
> ① 条码 / 成本 / 体积 / 重量 / 内部参考号的**真身在变体记录上**，而本模块的铁律是「保留原 `product.product` 记录（id 不变）」——转换后那条默认变体天然带着全部原值，一个字节都不用搬；
> ② 销售价 / 税 / 计量单位 / 纸箱与产品尺寸**本来就在模板上、全变体共享**，转换根本不碰。
> 唯一会变的是**查看位置**：产品表单上那几个字段在多变体状态下读出来是空 / 0，真值在对应变体上（详见下表与下方说明）。

机制先讲清楚，否则表格看不懂。Odoo 19 里 `product.product` 通过 `_inherits = {'product.template': 'product_tmpl_id'}` **委托**模板字段；
而 `barcode` / `standard_price` / `volume` / `weight` / `default_code` 这几个是 `product.product` **自己声明的存储字段**，在变体上**覆盖**了委托来的模板字段。
于是模板侧那几个变成「单变体桥接」：单变体时读 / 写都落到那条变体（`_compute_template_field_from_variant_field()` / `_set_product_variant_field()`），
一变多之后读出来是默认值（空 / 0）、写进去也不落任何变体 —— **这是 Odoo 原生语义，任何多变体产品都一样，与本模块无关**。

| 字段 | 后端真身（存储在哪） | 普通产品（单变体）时 | 转换后（多变体） | 默认变体上的值 | 需要迁移？ |
|------|----------------------|----------------------|------------------|----------------|------------|
| 内部参考号 `default_code` | **变体**（`product.product` 存储字段） | 产品表单显示那条变体的值 | 产品表单显示空；在这里改也不落库 | **原值保留** | 不需要 |
| 条码 `barcode` | **变体**（存储字段，唯一性按变体校验） | 同上 | 同上 | **原值保留** | 不需要 |
| 成本 `standard_price` | **变体**（存储字段，按公司隔离） | 同上 | 同上 | **原值保留** | 不需要 |
| 体积 `volume` | **变体**（存储字段） | 同上 | 同上 | **原值保留** | 不需要 |
| 重量 `weight` | **变体**（存储字段） | 同上 | 同上 | **原值保留** | 不需要 |
| 销售价 `list_price` | **模板**（变体侧只是 `related='product_tmpl_id.list_price'` 的委托） | 产品表单显示模板价 | 产品表单不变 | 全变体共享同一价 | 不需要 |
| 属性加价 `price_extra` | 属性取值（`product.template.attribute.value`） | — | — | 随取值自动带上 | 不需要 |
| 纸箱 / 产品尺寸（`product_packing`） | **模板**（普通存储字段） | 产品表单 | 产品表单不变 | 全变体共享 | 不需要 |
| 税 `taxes_id` / 计量单位 `uom_id` / 产品分类 | **模板** | 产品表单 | 产品表单不变 | 全变体共享 | 不需要 |

**所以「转换后我的条码 / 成本 / 重量去哪了」的标准答案**：没丢，仍在原来那条变体记录上——也就是弹窗里被指定承载库存与单据的那条。
去**变体表单或变体列表**看和改（产品表单上的这几个字段在多变体产品上本来就不代表某一条变体）。

> 字段层级由自动化测试 `test_field_storage_layers_match_the_audit()` 钉住：Odoo 升级若改动存储层级，测试会先失败，提醒重新评估是否需要迁移。

### 价格与库存的同步规则

**库存：一个字都不动。** 不拆分、不合并、不迁移，新变体从 0 开始；这就是「保留原 `product.product` 记录」换来的结果。

**转换不会搬运的价格类数据**（上面审计表之外的补充）：

| 数据 | 归属 | 转换后的结果 |
|------|------|--------------|
| 供应商价格 `product.supplierinfo` | 可只挂某条变体，也可挂整个模板 | **默认按变体分离**：模板级的记录拆成每条变体一份（数值不变），新变体再从谱系来源继承一份；勾选「应用到全部变体」才统一为模板级同一批数值（见下方 ⚠） |
| 价格表规则 `product.pricelist.item` | `applied_on = 0_product_variant` 只管一条变体，`1_product` 管整个模板 | **按变体分离**：本产品模板级的规则拆成每条变体一份（数值不变），新变体从谱系来源继承 |
| 成本 `standard_price` | 变体级（见审计表） | 既有变体各自保留；新变体按谱系继承来源（见下节「新变体继承策略」） |

### 新变体继承策略（默认开启，可关）

新变体不是「凭空一条空记录」：默认会从它的**谱系来源**（`Derived From`，即它与之一致的那条既有变体）复制下面这三样变体级数据。

| 字段 | 是否继承 | 为什么 |
|------|----------|--------|
| 成本 `standard_price` | ✅ 继承来源 | 新规格通常成本相近；不继承就是 0，毛利报表会失真 |
| 体积 `volume` | ✅ 继承来源 | 外贸算运费要用，宁可先给一个可改的值，也别是 0 |
| 重量 `weight` | ✅ 继承来源 | 同上 |
| 内部参考号 `default_code` | ❌ 不继承 | 本仓库 `product_reference` 的 L1 约束是「**多变体产品不共用参考号**」，复制会与它冲突；新变体应各有可区分的参考号 |
| 条码 `barcode` | ❌ 不继承 | `product.product.barcode` 有**唯一性约束**（`_check_barcode_uniqueness()`），复制必然报错 |
| 价格表规则 `product.pricelist.item` | ✅ 按变体分离后从来源继承 | 本产品模板级规则先拆成每条变体一份，新变体再继承它来源那份 —— 每个变体的售价都能各自改 |
| 补货规则 `stock.warehouse.orderpoint` | ❌ 不继承 | 每个仓库 / 位置一条，复制容易造成重复补货；需要时给新变体单独建 |
| 供应商价格 `product.supplierinfo` | ✅ 默认分离：新变体继承来源一份；勾选「应用到全部变体」时改为所有变体共用同一批 | 见上文「价格数据按变体分离」 |

**关闭方式**：系统参数 `product_variant_conversion.inherit_variant_data` 设为 `0`（或 `false` / `no` / `off`）→ 新变体的成本 / 体积 / 重量保持 Odoo 默认的空 / 0，完全由你自己填。

**谱系来源为空时**（判定不唯一）不复制、保持空值——宁可留空让你填，也不乱指一个来源。是否继承了数据会记在转换台账的 **Variant Data Inherited** 列上，可追溯。

> ⚠ **供应商价格共享的代价**（勾选框**默认不勾选**，要主动勾才会发生）：同一供应商若对不同既有变体给了**不同价格**（例如红色 10、蓝色 12），勾选共享后两条都会变成「适用于全部变体」的同级价格记录；采购取价按「折后价 → 序号 → id」排序，只会用上其中一条（通常是便宜的那条）。**要保留变体级价差，就不要勾选共享。**

### 价格数据按变体分离（默认）

**模板级的价格记录 = 一条记录被所有变体共用**：改一次就影响全部变体，这与「变体的价格要各自独立」冲突。所以转换**默认把价格数据按变体分离**：

| 数据 | 转换后 |
|------|--------|
| 本产品**模板级**的供应商价格 / 价格表规则 | 按变体各复制一份（**数值完全不变**）后，**删除原来那条模板级记录** —— 从此每条变体一份，各自可改 |
| 已经**按变体**的记录（`supplierinfo.product_id`、`pricelist.item.applied_on = 0_product_variant`） | 不动（本来就已经分离） |
| **新变体** | 从它的谱系来源（`Derived From`）继承一份，来源没有就留空 |
| `3_global`（所有产品）/ `2_product_category`（按分类）的价格表规则 | **绝不触碰**（它们不属于本产品） |

两条安全线：

1. **绝不静默改价** —— 若变体在同一「价格表 + 数量门槛」上已有自己的规则，模板级规则不再拆过去（否则会凭空多出一条同档规则、把原来生效的那条挤掉）。
2. **后置断言**：分离前后逐条变体校验「供应商价格只多不少」「原有变体的**实际售价**一分未变」「新变体的售价与其来源一致」，不符即整单回滚。

**关闭方式**：系统参数 `product_variant_conversion.separate_variant_prices` 设为 `0`（或 `false` / `no` / `off`）→ 模板级记录保持模板级（所有变体共用，改一条影响全部）。是否分离会记在转换台账的 **Variant Prices Separated** 列上。

> 想在转换时反过来把价格**统一**给全部变体？在弹窗里勾选「把这些变体的供应商价格应用到全部变体」即可（供应商价格回到模板级一份；价格表规则仍按变体分离）。

## 使用前提与限制

- 产品必须有**至少一个变体**，且不是组合产品（`type != 'combo'`）
- 产品**不能有已归档变体**：请先恢复或删除。否则 `_create_variant_ids` 可能把老变体重新激活，归属会变得不可控
- 产品**不能有「按需生成」的属性**（`attribute.create_variant == 'dynamic'`）：那种情况下变体由 Odoo 按订单自动创建，不需要本弹窗
- **不能通过本流程删取值 / 删属性**：这类改动会让既有变体失去归属，一律拒绝。确实要删，请先归档或删除不想要的变体，再改属性配置
- **一次只能保存一个产品**：多记录写入无法逐条记录归属，会被拒绝
- 变体数受系统参数 `product.dynamic_variant_limit`（默认 1000）限制，超限会直接拒绝并说明数量

## 已知边界与后续迭代

### 已知边界（当前实现如此，不是 bug）

| 边界 | 说明 |
|------|------|
| 只拦「产品表单改属性」这一条路 | 归属确认挂在 `product.template.write()` 上。**在属性主数据里删 / 归档属性取值**走的是另一条路（`product.template.attribute.value.unlink()` → `_unlink_or_archive()`），**会直接删除或归档既有变体**，不经过本模块；直接写 `product.template.attribute.line` 的代码（其它模块 / 脚本）也会触发它自己的 `_create_variant_ids()`。见「后续迭代」第 1 条。 |
| 弹窗不显示在手数量 | 预览接口**已经返回**每条既有变体的在手数量（`preview.variants[].on_hand`），当前弹窗只用到名称，没有展示。见「后续迭代」第 4 条。 |
| 继承范围有限 | 新变体按谱系继承**成本 / 体积 / 重量**与**价格数据**（价格表规则、供应商价格）；参考号、条码、补货规则刻意不继承（各有硬约束，见「新变体继承策略」）。来源为空时也留空，不猜测。 |
| 分离会拆掉模板级价格记录 | 默认分离时，本产品模板级的供应商价格 / 价格表规则被**拆分后删除**（值完整保留在各变体上，后置断言保证售价一分未变）。不想拆就关掉系统参数 `product_variant_conversion.separate_variant_prices`。 |
| 供应商价格共享会抹平变体级价差 | 见上文 ⚠（勾选框默认不勾选，不会自动发生）。 |
| 谱系行随变体级联删除 | `product.variant.lineage` 的两个变体字段是 `ondelete='cascade'`：删掉一条变体，它在谱系里的行会一起消失（转换台账本身不受影响）。 |
| 组合数特别大的产品 | 组合枚举没有前置上限保护，会先枚举出全部组合、再撞 `product.dynamic_variant_limit`；超大产品请先精简属性取值。 |
| 无法撤销一次转换 | Odoo 没有内置回滚，转换前请备份。 |

## 国际化（i18n）

- **源语言：英文（`en_US`）**，源码（Python / XML / JS / QWeb 模板）里一律写英文；中文只出现在 `i18n/zh_CN.po` 的 `msgstr`。
- 覆盖范围：字段标签 / help、模型名、视图文案（含页面、按钮、列表列）、弹窗模板文本与 JS `_t()`（选项标签、提示句）、Python 端的校验与报错信息。
- **应用列表（Apps）元数据**：模块名 / 摘要 / 描述的中文由 `i18n/zh_CN.po` 的 `model:ir.module.module,shortdesc|summary|description:base.module_product_variant_conversion` 三条提供，分类沿用官方的 `Inventory/Product`（自定义段 `base.module_category_inventory_product` → 「产品」，与其它产品类模块合并同一条 `msgid`）。改 `__manifest__.py` 的 `name` / `summary` / `description` 时必须同步这三条，规范见根 [`AGENTS.md`](../AGENTS.md) 4.8。
- 占位符统一 `%(name)s` 命名形式，禁止按位置拼接；弹窗里夹在元素中的句子（如「还差 N 条」）一律在 JS 侧用 `_t()` 拼好再 `t-esc`，避免被模板切成碎片。
- 改动流程：改英文源文本 → 用官方 `odoo i18n export` 重导出术语骨架 → 按 `msgid` 合并回 `i18n/zh_CN.po` → `task check` → `-u` 升级 + 强刷浏览器，英文与中文各验一遍（做法见模块 `AGENTS.md` → L2 P3）。
- 本模块 `i18n/zh_CN.po` 现有 110 条 `msgid`（107 条来自官方导出骨架 + 3 条应用列表元数据），`msgid` 与源码逐字符一致；只有 6 条标准审计字段标签（`Created by` 等，界面上不显示）没有译文。

## 安装与使用

### 全新安装

1. 将 `product_variant_conversion` 目录放入 Odoo 19 的 `addons_path`
2. 更新应用列表后安装模块：**产品变体转换**
3. **强刷一次浏览器**（Ctrl+F5）：本模块的保存拦截与弹窗是前端资源，必须让页面加载到最新资产

### 从旧版本升级

`19.0.2.0.0` 及更早的版本用的是「产品表单按钮 + 向导」。`19.0.3.0.0` 起改为「保存时拦截 + 弹窗」，向导模型（`product.variant.conversion.wizard` 等）已删除：瞬态模型，无数据迁移，**不需要迁移脚本**；升级后请强刷浏览器，并确认产品表单上原来那个按钮已经消失。

### 操作

- 改属性 → 保存 → 需要时在弹窗里确认归属 → 保存继续
- 转换完成后到 **Variant Lineage** 页核对，或点 **Conversions** 看台账

### 自动化测试

```bash
# 只测产品侧（不装 stock / sale）
task test -- product_variant_conversion --test-tags=/product_variant_conversion

# 连库存 / 销售一起验证（推荐，会额外装上 stock 与 sale_management）
task test -- product_variant_conversion,stock,sale_management --test-tags=/product_variant_conversion
```

### 异常情况与处理

- **点保存弹出危险提示「会归档或删除 N 条既有变体」**：说明这次属性改动是删减类的。先归档或删除不想要的变体，再改属性配置。
- **点保存报错说「需要在产品表单里确认归属」，但没看到弹窗**：前端资源没生效，强刷页面（Ctrl+F5）后再保存一次。
- **弹窗里 `Confirm` 点不动**：还有既有变体没被分配组合，弹窗底部会提示还差几条；每条既有变体必须恰好承载一个组合。
- **报「有归档变体」**：先在产品变体列表里恢复或删除它们，再改属性。
- **报「按需生成变体」**：把该属性的「变体生成方式」改为「立即」。
- **想撤销一次转换**：Odoo 没有内置回滚。可在转换后立刻把新变体归档并删掉多余属性取值（原生界面会给出警告），或从备份恢复；**转换前请先备份**。
